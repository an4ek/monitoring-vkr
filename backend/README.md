# Бэкенд

Django + Django REST Framework (API-сервер). События проходят конвейер в PostgreSQL: прием в первую таблицу, пачкой в поток TimescaleDB, разбор в кэше и перенос в CMDB на PL/pgSQL. Брокера сообщений нет; по умолчанию конвейер запускается в транзакции вставки, при необходимости — отдельным процессом `pipeline_worker`.

| Приложение | Что внутри |
|---|---|
| `api/` | Каталог (отделы, сотрудники, сервисы, ресурсы с зависимостями), инциденты, история, события; API на чтение; тестовые данные (`load_mocks`) |
| `processing/` | Прием событий от Zabbix и Alertmanager; конвейер в базе (миграция `0006`: landing → поток TimescaleDB → кэш → CMDB → архив); функции группировки в инцидент, первопричины, состояния сервисов и автозакрытия (миграция `0005`); эталон на Python в `logic.py`; функции рассылки оповещений (автоматически не вызываются), кнопки «Взять в работу» и «Закрыть», подписки |
| `accounts/` | Вход по логину и паролю, роли: администратор, инженер, руководитель |

## Запуск

Сначала поднять инфраструктуру (PostgreSQL + TimescaleDB, Mailpit): `cd infra && docker compose up -d`.

```
cd backend
python -m venv venv
venv\Scripts\activate            # Windows   (Linux/macOS: source venv/bin/activate)
pip install -r requirements.txt
python manage.py migrate
python manage.py demo_reset      # тестовые данные
```

Дальше нужен только API-сервер: по умолчанию конвейер работает в транзакции вставки, отдельный обработчик не нужен.

```
python manage.py runserver                 # API-сервер, http://localhost:8000/api/
```

И фронтенд: `cd frontend && npm run dev`, открыть http://localhost:5173.

## Показ: авария коммутатора

```
python manage.py demo_reset              # вернуть тестовые данные в исходное состояние
python manage.py demo_failure            # прислать события о сбое (как Zabbix и Alertmanager)
python manage.py demo_failure --recover  # прислать события о восстановлении
```

Что увидеть:

1. В журнале инцидентов через несколько секунд появляется новый инцидент. Сначала первопричина `web-01`, а когда приходит событие о коммутаторе, она меняется на `sw-core-01`.
2. В карточке инцидента пять событий: коммутатор отмечен как первопричина, остальные как следствия. На странице «Сервисы» сайт и 1С в состоянии «Не работает».
3. В Mailpit (http://localhost:8025) лежат письма: Иванову — «Устранить», остальным — «К сведению».
4. Войти как инженер (`ivanov`) и нажать «Взять в работу», затем «Закрыть». В журнале и карточке видно, кто взял и кто закрыл. Под руководителем (`orlova`) и администратором (`admin`) этих кнопок нет.
5. Или вместо ручного закрытия выполнить `demo_failure --recover`: инцидент закроется сам, сервисы вернутся в «Работает».

Проверки: `python manage.py test processing accounts`.

## Вход и роли

`demo_reset` создает тестовых пользователей, пароль у всех `demo12345`:

| Логин | Роль | Что может |
|---|---|---|
| `admin` | Администратор | Смотреть журнал; пункт меню «Администрирование» — пользователи, роли и каталог (админка Django) |
| `ivanov`, `petrova` | Инженер | Брать инциденты в работу и закрывать их, свои подписки |
| `orlova` | Руководитель | Назначать ответственных за ресурсы и сервисы (кнопка «Назначить» в каталоге и на странице сервисов), смотреть журнал, свои подписки |

Без входа API отдает только `/api/health/`. Вход по сессии Django: cookie сессии недоступна JavaScript, изменяющие запросы защищены CSRF-токеном.

## Прием событий

| Адрес | Кто присылает | Формат |
|---|---|---|
| `POST /api/events/zabbix/` | Zabbix, способ оповещения «Webhook» | `{"event_id": "{EVENT.ID}", "status": "{EVENT.VALUE}", "host": "{HOST.HOST}", "name": "{EVENT.NAME}", "severity": "{EVENT.NSEVERITY}"}` |
| `POST /api/events/alertmanager/` | Alertmanager, `webhook_configs` | стандартный формат Alertmanager; ресурс берется из метки `resource` или `instance` |

Все события одного запроса пишутся одной пачкой (один `INSERT ... VALUES`), после чего срабатывает конвейер. По умолчанию ответ `202 Принято` приходит после обработки пачки: конвейер запускается в той же транзакции, что и запись. В асинхронном режиме (`processing.pipeline_autostart = 'off'`) ответ означает только прием в первую таблицу. Мониторинг обязан передавать секретный ключ в заголовке `X-Webhook-Token`, иначе ответ `403`. При разработке ключ `dev-webhook-token`.

## Конвейер обработки (PL/pgSQL + TimescaleDB)

Схема:

```
вебхук
  └─> processing_incomingevent      первая таблица, только прием
        └─> processing_eventstream  поток, hypertable TimescaleDB
              └─> processing_eventcache  кэш обработчика (UNLOGGED)
                    └─> api_* (CMDB)   инциденты, события, состояния
                          └─> processing_eventarchive  архив сырых событий
```

Конвейер создает миграция `processing/0006_event_pipeline.py`; функции группировки, первопричины и автозакрытия остаются из `0005_plpgsql_processing.py` и используются как обработчик.

1. Вебхук пишет пачку в `processing_incomingevent`. Статус `new`, `enqueued_at` пока пуст.
2. AFTER INSERT STATEMENT-триггер `processing_incomingevent_pipeline` вызывает `processing_pipeline_run()`. Перенос в поток — один `INSERT ... SELECT` пачкой, без построчной обработки. Если событий больше `processing.pipeline_batch_size`, триггер повторяет проход, пока не разберет всю пачку.
3. `processing_eventstream` — поток. При установленном расширении TimescaleDB это hypertable с разбиением по `received_at` (сутки). Без расширения — обычная таблица, конвейер работает так же.
4. `processing_cache_fill()` складывает пачку в `processing_eventcache` и сразу сопоставляет `resource_name` с ресурсом каталога (`ci_id`).
5. `processing_cache_apply()` вызывает PL/pgSQL-обработчик, переносит результат в CMDB, очищает кэш и перекладывает сырые строки потока в `processing_eventarchive`.
6. Статус события, `processed_at` (через `clock_timestamp()`), `attempts` и текст ошибки обновляются в первой таблице.

Ошибка одного события не откатывает пачку: для него откатывается только обработка, ставится статус `failed` с текстом ошибки, а сырые данные уходят в архив. Повтор берет исходное событие из первой таблицы:

```
python manage.py reprocess_events
```

или

```
docker exec -it vkr-postgres psql -U monitoring -d monitoring -c 'CALL reprocess_failed();'
```

Настройки:

- `processing.group_window_minutes` — окно склейки в минутах, по умолчанию 5. Отдельно от `EVENT_GROUP_WINDOW_MINUTES`; действует для новых подключений.
- `processing.pipeline_batch_size` — размер пачки конвейера, по умолчанию 1000. В синхронном режиме пачка больше лимита обрабатывается несколькими проходами.
- `processing.pipeline_autostart` — `off` переводит конвейер в асинхронный режим: триггер только складывает пачку в поток, а обработчик запускается отдельно:

  ```
  ALTER DATABASE monitoring SET processing.pipeline_autostart = 'off';
  python manage.py pipeline_worker
  ```

  Для разового прохода (например, из cron): `python manage.py pipeline_worker --once`.
- `processing.trigger_off = 'on'` отключает триггер целиком. Он нужен только тестам, которые проверяют эталон на Python.

Ограничение: отмена запроса или таймаут (`query_canceled`, например `statement_timeout`), обрыв соединения и ошибка внутри самого обработчика ошибок не перехватываются. Тогда откатывается вся транзакция вместе с пачкой, вебхук отвечает `500`, и мониторинг присылает события повторно.

## Настройки (переменные окружения)

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `POSTGRES_HOST`, `POSTGRES_PORT` | `localhost`, `5432` | База данных |
| `EMAIL_HOST`, `EMAIL_PORT` | `localhost`, `1025` | Почта (Mailpit) |
| `MATTERMOST_WEBHOOK_URL` | пусто | Входящий вебхук канала Mattermost; пусто — в Mattermost не пишем |
| `EVENT_GROUP_WINDOW_MINUTES` | `5` | Окно группировки событий в инцидент для эталона на Python; в базе — `processing.group_window_minutes` |
| `WEBHOOK_TOKEN` | `dev-webhook-token` (только при разработке) | Ключ для приема событий |
| `DJANGO_DEBUG` | `1` | `0` на сервере: тогда обязательны свои `DJANGO_SECRET_KEY` и `WEBHOOK_TOKEN`, а `demo_reset` не работает |
| `DJANGO_SECRET_KEY` | ключ разработки | Секретный ключ Django |
| `DJANGO_ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` | `localhost,127.0.0.1`, `http://localhost:5173` | С каких адресов можно обращаться |

## Что пока упрощено

- **Рассылки в этой ветке нет.** Конвейер не принимает решения об оповещении, а функции в `processing/tasks.py` никто не вызывает автоматически, поэтому письма и сообщения об инцидентах не уходят. Ветка нужна для сравнения обработки по времени, как рабочую систему ее не выкладывать.

- Пользователями и ролями администратор управляет через админку Django, отдельной страницы на сайте пока нет.
- Нет ограничения числа попыток входа.
- Правило состояния сервиса временное: критичный сбой ресурса — «Не работает», некритичный — «С проблемами».
